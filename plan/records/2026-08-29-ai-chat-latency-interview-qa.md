## 一、核心问题应答框架

### Q：「这些优化数据是怎么测的？」

面试官意图：验证数据真实性、测量方法科学性、你是否真正理解自己的优化。

**回答（总—分—总，约 1 分半）：**

**总起**：这些数字不是估算的，全部来自实测。做法分三层：**接口级时间线拆解 → 隔离变量的对照实验 → 优化前后同环境复测**。

**第一层：SSE 事件时间线拆解**
我写了一个 Python 探针脚本，直接调用线上接口，登录拿 token，逐行解析 SSE 流，给每个事件打时间戳——thinking 阶段事件、response 分片、done 帧。这样一次请求的 49 秒就被精确拆解成：路由判断 2 秒、HyDE 40 秒、检索 2 秒、重排序 0.2 秒、Agent 首轮 11 秒。同时后端日志里本来就有每阶段的 INFO 日志（HyDE 开始/完成、检索到几篇文档），两边的**时间戳互相印证**，确保拆解没拆错。

**第二层：隔离变量的对照实验**
时间线告诉我"HyDE 慢"，但要证明"为什么慢"，我绕开业务代码**直接调 DeepSeek API 做受控实验**，一次只改一个变量。比如：同一个 HyDE 提示词，不加 max_tokens 是 13.6 秒生成 1481 字；加 max_tokens=150 是 1.7 秒生成 54 字——这就证明了瓶颈是"无输出长度限制导致超长生成"，而不是网络或业务代码。再比如 Agent 首轮，真实规模 prompt（2000+ tokens + 8 个工具定义）3.6 秒，短 prompt 只要 1.3 秒——证明 prompt 长度是重要因素。

**第三层：优化后复测**
改完代码，在**同一个环境、同样的查询、同一个测试账号**下重跑探针。24 秒到 8 秒，就是同一个查询「什么是向量数据库」的前后对比。因为 DeepSeek 服务端延迟波动很大，我测了多个查询、多轮，报告里给的是典型值而不是挑一个最好看的数。

**收尾**：所以我的每个结论——包括"重排序不是瓶颈、embedding 不是瓶颈"——都是先被测量排除掉的，不是拍脑袋。

## 二、预判追问与应对（背熟）

| 追问 | 应对 |
|---|---|
| "重排序 0.24s 你怎么测的？" | 探针时间线 + 后端日志双重确认；它是本地 CrossEncoder CPU 推理 5 个文档，还区分了 Redis 缓存命中（0.01s）和未命中（0.24s）两种情况 |
| "为什么 Agent 首轮 11 秒，你却说是 DeepSeek 慢？" | 有对照组：直连 DeepSeek 短 prompt 只要 1 秒，长 prompt 3.6 秒；真实链路里 2.7~11.2 秒的波动是服务端排队，本地能压的（prompt 长度）已经压到极限 |
| "假流式你是怎么发现的？" | 两处证据：读代码发现 `astream` 只收集完整 output、按 15 字/30ms 播放；探针显示检索完成后 **8.7 秒**才出现第一个非空 response——代码和现象对上了 |
| "数据波动大，会不会测不准？" | 报告给的是区间和典型值，并且把波动来源（上游 API）和本地可控部分分开标注；优化前后是同环境对比，波动不影响结论 |
| "用没用 profiling 工具（cProfile/py-spy）？" | 诚实说：没用。瓶颈在**跨服务调用**（LLM API 返回慢），应用层时间线 + 对照实验已经足够定位；本地 CPU 环节（重排序 0.24s）实测确认不是瓶颈，才不需要深入 profiling |
| "测量有没有可能自证偏差？" | 对照组设计 + 冷热状态分开（冷启动首字节 2s vs 热态 0.05s 是模型加载，不算瓶颈）+ 日志交叉验证，每个数字都能指到出处 |

## 三、加分细节（可以主动说）

1. **环境问题发现**："验证时还发现一个环境问题：两个后端实例同时加载 2GB 重排序模型会内存竞争导致崩溃，所以性能验证要注意环境隔离。"——展示你不仅会测，还会发现测量环境本身的问题。
2. **全链路理解**："前端感知和网络耗时我也区分了：前端有 3 条消息缓冲 + rAF 合并，所以 token 级高频事件不会卡 UI。"——展示你懂全链路，不止后端。

## 四、注意点

- **不要主动提**"pytest 沙箱跑不了、用了替代方案"——面试官会觉得验证环境很怪。
- 如果被问到测试：回答"编排层测试用 FakeAgentExecutor 模拟 token 流断言帧序列，另外用内存 SQLite 做了完整链路验证"即可，这是标准做法，没有任何需要解释的地方。

## 六、方法论提炼（简历/面试通用）

这套测量方法不只适用本项目，可迁移到任何"慢接口"排查：

1. **从用户视角建立完整时间线**（SSE/响应事件逐段打点）——先知道"慢在哪一段"，而不是猜
2. **对每个可疑环节做隔离实验**（直连依赖、一次只改一个变量）——证明"为什么慢"
3. **优化前后同环境复测**——量化"改了多少"（Δ 指标）
4. **主动排除非瓶颈**（测出快的环节也要记录）——避免别人质疑"你怎么知道不是它"
5. **如实标注不可控波动**（上游 API）——把"本地可控"与"上游限制"分开，展示判断力
