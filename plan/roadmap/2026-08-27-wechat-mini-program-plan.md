# 微信小程序版实施规划

> 创建：2026-08-27
> 背景：云舒卷（RAG Notebook）当前为 Web SPA（React 19 + FastAPI）。若需上线微信小程序版，按本规划执行。
> 原则：**后端复用约 80%，前端按小程序生态重写；微信登录体系需新增；分阶段交付、每阶段可独立验证。**

---

## 1. 复用性评估

| 层 | 复用度 | 说明 |
| --- | --- | --- |
| FastAPI 后端 | ~80% | 纯 HTTP API 可直接被小程序调用；仅需新增微信登录接口 |
| 数据层（MySQL/Redis/ChromaDB） | 100% | 完全复用，账号体系打通即可 |
| RAG / AI / 社交能力 | 100% | 后端接口不变（SSE 需小程序端适配） |
| 前端 React 代码 | ~0% | 小程序无法运行 React DOM，需按 Taro/原生重写 |
| 登录体系 | 需改造 | 微信小程序必须走 `wx.login` 换 openid 的登录链路 |

---

## 2. 前端技术路线（三选一）

| 方案 | 说明 | 适合 |
| --- | --- | --- |
| **Taro（React 语法）⭐推荐** | 支持 React 写法，现有组件逻辑/状态管理（Zustand）/hooks 概念可平移，学习成本最低 | 团队熟 React（本项目即是） |
| uni-app（Vue 语法） | 生态最全，一套代码多端（小程序/H5/App） | 想顺带出 App/H5 |
| 原生小程序（WXML/WXSS） | 性能最好、无框架层，全部手写工作量最大 | 对性能极致要求 |
| web-view 套壳（过渡） | 内嵌 webview 打开现有 H5 | 临时演示，不推荐（体验差、域名白名单限制、审核风险） |

> 推荐 **Taro + React**：axios 封装 → Taro.request、页面结构重构，但业务逻辑（API 层、Zustand store、双链、卡片生成逻辑）可大量平移。

---

## 3. 必须解决的技术点

### 3.1 后端上线（前置条件，阶段 0）
- [ ] 云服务器 + 域名 + **HTTPS 证书**（小程序强制 https 且域名已备案）
- [ ] Nginx 部署：改造 `deploy/nginx.conf.example` 为线上域名版（静态资源 + `/api` 反代 + `/public` + `/media`）
- [ ] 后端多 worker 生产启动（`backend/start_prod.ps1` 已就绪，部署到 Linux 需等价 shell 脚本）

### 3.2 微信登录接入（阶段 1）
- [ ] `users` 表新增 `openid` 字段（唯一索引），支持一 openid 对一用户
- [ ] 后端新增 `POST /auth/wechat`：body `{code}` → 调微信 `code2session` 换 openid → 查/建用户 → 返回现有 JWT（token 体系复用，`get_current_user_id` 不变）
- [ ] **账号打通**：小程序登录后支持「绑定已有账号」（openid 关联 Web 用户 id），保证 Web/小程序数据互通（笔记/动态/养成数据同一份）
- [ ] 前端小程序：`wx.login()` 拿 code → 调 `/auth/wechat` → 存 token

### 3.3 小程序端适配
- [ ] 小程序后台配置 request 合法域名（`https://你的域名`）；`/media` 图片域名单独配置
- [ ] 图片上传：`wx.uploadFile` 对接现有 `/file/upload/`；返回 URL 需为域名形式（不能用 IP/端口）
- [ ] **SSE 流式对话适配**：小程序 `wx.request` 不支持原生 SSE → 方案 A：`enableChunked: true` 分块读取（基础库 2.20+）；方案 B：后端加轮询模式（推荐稳妥）
- [ ] 包体积：主包 ≤ 2MB，图表/编辑器重依赖按需引入或裁剪

### 3.4 功能裁剪（MVP 范围）
| 保留（核心） | 简化/裁剪（二期） | 暂不做 |
| --- | --- | --- |
| 登录/笔记列表/详情/编辑（textarea + markdown 预览） | 知识仪表盘（简化数字卡片） | 知识图谱（d3 太重） |
| 间隔回顾打卡 + AI 出题 | 动态流（文字为主，图片压缩上传） | Canvas 分享卡片（可后续） |
| AI 对话（流式/轮询） | 番茄钟（页面版） | Tiptap 编辑器（移动端体验差） |
| 好友/关注/通知（列表化） | 页宠简化版（静态形象 + 好感度） | 命令面板 ⌘K（无键盘） |
| 养成数据同步（复用 `/user/settings/`） | 知识广场（列表化） | — |

### 3.5 审核与合规
- [ ] 小程序类目选择（工具 / 教育）
- [ ] 用户隐私保护指引（收集头像昵称/位置等需声明）
- [ ] 内容安全：现有敏感词 + LLM 审核可复用；图片建议接微信 `security.imgSecCheck`（可选）

---

## 4. 推荐路线图

```
阶段 0（3~5 天）  后端上线：服务器 + 域名备案 + HTTPS + Nginx 部署现有 API
阶段 1（2~3 天）  微信登录：users.openid + POST /auth/wechat + token 复用 + 账号绑定
阶段 2（2~3 周）  小程序 MVP（Taro）：登录 → 笔记 → 回顾 → AI 对话 → 养成同步
阶段 3（1~2 周）  迭代：动态/广场/番茄钟/页宠简化版 → 提审上线
```

**总预估：1~1.5 个月业余时间**（前端重写为大头；后端工作量集中在阶段 0/1，约 1 周）。

## 5. 后端新增接口清单（阶段 1）

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/auth/wechat` | POST | body `{code}` → openid 登录/注册 → 返回 `{token, user}` |
| `/auth/wechat/bind` | POST | 小程序账号绑定已有 Web 账号（body `{code, username, password}`） |
| `/user/settings/` | 已有 | 养成数据同步（无需改动） |
| 现有全部 API | — | 除登录外零改动 |

---

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 小程序无法跑 React DOM | 选 Taro（React 语法）平移动逻辑，组件重写 |
| SSE 流式不兼容 | 后端加轮询模式或 `enableChunked` 分块读取 |
| 包体积超限 | 主包放核心页，社交/图表页分包加载 |
| 域名/备案周期长 | 提前 1~2 周开始备案（阶段 0 首件事） |
| Web 与小程序账号割裂 | openid 绑定机制 + 同一 users 表 |
| 提审被拒（类目/隐私） | 提前准备隐私指引与类目材料 |

---

## 7. 与现有架构的契合点（已就绪）

- 养成数据上云（`/user/settings/`）→ 小程序天然继承
- JWT 体系与用户隔离 → 后端零改动复用
- 双层内容审核 → 小程序内容直接复用
- Nginx 部署示例 → 改域名即可上线
- 测试账号/接口文档 → 小程序联调用

---

## 8. 决策点（开工前确认）

1. 前端框架：Taro（推荐）vs uni-app vs 原生
2. 账号体系：小程序独立账号 vs 绑定 Web 账号（推荐绑定，数据互通）
3. MVP 范围：按 §3.4 裁剪表执行 or 调整
4. 服务器：现有本机 or 云服务器（含域名备案）
