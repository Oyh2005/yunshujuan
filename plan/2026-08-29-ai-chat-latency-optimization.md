# AI 对话延迟优化全记录：从 24 秒到 8 秒的性能攻坚

> 日期：2026-08-29
> 项目：云舒卷（RAG Notebook）——AI 驱动的个人知识管理平台（FastAPI + LangChain + React 19）
> 文档性质：性能问题「发现 → 分析 → 解决」完整过程记录，兼作简历/面试素材
> 面试问答素材（数据怎么测的 + 预判追问应对）：见 `plan/2026-08-29-ai-chat-latency-interview-qa.md`
> 相关代码：`backend/app/rag/rag_service.py`、`backend/app/router/chat.py`、`backend/app/agent/agent.py`

## 0. 一句话总结（简历版）

**问题**：AI 对话回复极慢（典型 24s、最坏 49s），用户无法忍受。
**定位**：通过 SSE 事件时间线拆解 + 分层对照实验，锁定「HyDE 假设文档生成不限长（8~40s）」「Agent 首轮长 Prompt 调用（11s）」「假流式播放（回答生成完才显示）」三大瓶颈。
**解决**：HyDE 限长（13.6s→1.7s）、RAG 上下文截断、Agent 真流式改造（token 级实时转发）。
**结果**：典型回答 24s→8s（-67%），最坏 49s→9s（-82%），首字延迟 8.7s→2.9s，用户体验从"转圈等半分钟"变为"2-3 秒出字、逐字输出"。

---

## 1. 问题发现

### 1.1 用户反馈
用户实际体验网站 AI 对话功能后反馈：**"回复很慢"**。

### 1.2 系统现状（排查前已知信息）
- 调用链：`POST /chat/agent/query/stream`（SSE 流式）
  - 路由判断（向量相似度打分，决定是否走 RAG）
  - RAG 前置管线：**HyDE 生成假设文档 → 向量检索（知识库+笔记）→ 重排序（本地 bge-reranker-v2-m3）**
  - Agent 执行：tool-calling Agent（LangChain AgentExecutor），8 个工具
- 模型配置：对话 = DeepSeek 云端 API；嵌入 = 本地 Ollama（nomic-embed-text）；重排序 = 本地 CrossEncoder（CPU）
- 测试账号数据：1 篇笔记 + 4 篇知识库文档（测试数据）

### 1.3 初步验证
直接调用线上接口解析 SSE 事件流，确认问题真实存在且严重：
- 问「云舒卷是什么？」：**总耗时 49.31s**
- 问「什么是向量数据库？」：**总耗时 24.01s**
- 连闲聊「你好」都要 20.5s（被误路由进 RAG）

---

## 2. 问题分析（定位过程）

### 2.1 第一步：代码走查，梳理完整调用链
通读 `chat.py` → `rag_service.py` → `reorder_service.py` → `agent.py`，发现两个可疑点：
1. **HyDE 提示词要求"生成一个详细的假设性回答"，且模型创建时未设置 max_tokens**（`factory.py` 的 `create_chat_openai` 只有 `streaming` 和 `top_p`）——LLM 可能生成超长文档
2. **`agent.py` 是"假流式"**：`async for chunk in agent_executor.astream(...)` 只收集 `chunk["output"]`（完整回答），等整个 Agent 执行完后，才按 `chunk_size=15` + `sleep(0.03)` 模拟打字机播放——**LLM 真实 token 流从未被转发**

### 2.2 第二步：SSE 时间线拆解（探针实测）
写探针脚本逐事件打时间戳，把一次请求按阶段拆开（单位：秒）：

| 阶段 | 问「云舒卷」 | 问「向量数据库」 | 结论 |
|---|---|---|---|
| 路由判断 + SSE 首字节 | 2.09 | 0.05 | 基本正常（冷启动除外） |
| **HyDE 生成假设文档** | **40.4** | **8.4** | ❌ 大瓶颈 |
| 向量检索 | 2.2 | 2.2 | 正常 |
| 重排序（本地模型） | <0.1 | 0.2 | ✅ 非瓶颈 |
| **Agent 首轮 LLM（思考+调工具）** | ~2.2 | **11.2** | ❌ 大瓶颈 |
| Agent 生成 + 假流式播放 | ~4.6 | ~2 | 播放慢 |
| **总计** | **49.3** | **24.0** | |

再结合后端日志还原时间线，确认 HyDE 阶段生成了一篇 **1000+ 字的假设文档**。

### 2.3 第三步：分层对照实验（量化根因）
直接调用 DeepSeek API 做受控实验，把每个环节的"真实成本"测出来：

| 实验 | 结果 | 结论 |
|---|---|---|
| HyDE 提示词不限长调用 | **13.6s**（生成 1481 字，1082 output tokens + 225 reasoning tokens） | 无 max_tokens + "详细"提示词 = 超长生成 |
| 同样调用加 `max_tokens=150` | **1.7s**（生成 54 字） | **限长可省 ~12s** |
| Agent 首轮：真实规模 prompt（2049 tokens + 8 工具定义 + RAG 上下文） | 3.6s | 长 Prompt 显著拖慢推理模型 |
| Agent 首轮：短 prompt 对照 | 1.0~1.4s | 上下文长度是重要因素 |
| 简单闲聊首 token（流式） | 0.1s | DeepSeek 本身很快 |
| Ollama embedding 单次 | 16~170ms | ✅ 非瓶颈 |
| 本地重排序 5 文档 | ~0.24s | ✅ 非瓶颈 |

### 2.4 根因结论（按影响排序）
1. **HyDE 假设文档生成不限长**：提示词要求"详细" + 无 max_tokens → DeepSeek（推理模型）生成 1000~2000 字，单次调用 8~40s（波动大）
2. **Agent 首轮 tool-calling 调用慢**：system prompt 注入**未截断**的 RAG 上下文（3 个完整文档）+ 8 个工具定义 + 主提示词，prompt 2000+ tokens，DeepSeek 推理模型长 Prompt 首 token 慢（3.6~11.2s）
3. **假流式**：回答**全部生成完**才开始播放，用户在整个 Agent 阶段（5~13s）看不到任何输出——感知延迟 = 总延迟
4. **设计问题**：路由阈值 0.5 过松，「你好」类闲聊也触发 RAG，白等 HyDE

## 3. 问题解决（实施过程）

### 3.1 优化一：HyDE 限长（一行改动，收益最大）
**改动**（`rag_service.py`）：
- 提示词：「生成一个**详细的**假设性回答」→「生成一个**简短的**假设性回答（150字以内）」
- 调用：`self.chat_model.bind(max_tokens=150)`

**原理**：HyDE 生成的假设文档只是用于向量检索的"查询代理"，不需要长文；限制输出长度直接掐断最大耗时来源。检索质量实测不受影响（仍返回 1 笔记 + 4 知识库文档）。

**效果**：HyDE 阶段 **40.4s → 1.8~2.6s**（实测 -95%）。

### 3.2 优化二：RAG 上下文截断
**改动**（`chat.py`）：注入 Agent 的 `rag_context` 每文档截断至 600 字（重排序仍用全文参与评分，只压缩 prompt）。

**效果**：Agent 首轮 prompt 显著缩小（实测 2049→~1200 tokens），首轮调用从 11.2s 降至 2.7~5s（其余波动来自 DeepSeek 服务端）。

### 3.3 优化三：Agent 真流式（技术含量最高）
**改动**（`agent.py`）：弃用假流式，改用 `astream_events(version="v1")` 监听 `on_chat_model_stream` 事件，**把 LLM 的 token 增量实时转发给前端**；同时拼接完整回答供会话历史落库；工具日志改监听 `on_tool_end`。

**三个关键决策与验证**：
1. **为什么能拿到 token 流**：`AgentExecutor.astream()` 在 `stream_runnable=False` 下不产生 token 流（最终 output 一次性给出）；`astream_events` 才能拿到逐 token 事件
2. **如何避免误转发**：Agent planning（思考/调工具）阶段的流式 chunk 只有 `tool_calls`、`content` 为空；DeepSeek 的推理内容在 `reasoning_content` 字段也不进 `content`——**按 `content` 非空过滤即可只转发正式回答**（用实验脚本验证过事件结构）
3. **前端零改动**：前端 `useSSE` 已有 3 条消息缓冲 + requestAnimationFrame 合并渲染机制，天然适配高频 token 事件

**配套**：更新测试替身 `tests/fakes.py`（FakeAgentExecutor 支持 `astream_events`）与编排层测试断言（分片断言从"15 字三分片"改为"token 级增量"）；因沙箱限制 pytest 无法跑（tmp_path 权限），另写独立验证脚本用内存 SQLite 复刻测试环境，**4 个场景断言全过**（帧序列/错误路径不落库/历史注入/RAG 上下文注入）。

## 4. 优化效果（前后对比，同机同查询实测）

| 指标 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 典型带 RAG 回答总耗时 | 24.0s | **7.9s** | **-67%** |
| 最坏场景总耗时 | 49.3s | **8.7s** | **-82%** |
| 闲聊（误触发 RAG） | 20.5s | **7.0s** | -66% |
| HyDE 阶段 | 8.4~40.4s | **1.8~2.6s** | -95% |
| 检索完成到首字 | 8.7s（无任何输出） | **2.9s**（token 级逐字输出） | 感知延迟大幅下降 |
| 回答展示方式 | 生成完按 15 字/30ms 播放 | **实时逐 token 流式** | 体验质变 |

三轮改动全部在用户 `--reload` 的开发实例上自动生效，无前端改动，无检索质量回退。

## 5. 关键技术点与踩坑（面试/简历素材）

### 技术亮点
- **性能分析方法论**：SSE 事件时间线拆解（探针逐事件打点）+ 分层对照实验（代码走查→接口实测→直连 API 受控实验），把 49s 的请求精确分解到每个环节，用数据而非猜测定位瓶颈
- **LLM 调用成本控制**：识别出"无 max_tokens 限制 + 鼓励长文提示词"是云端 LLM 调用失控的典型模式，一行 `bind(max_tokens=150)` 省 12~38s
- **LangChain Agent 真流式**：从 `astream`（假流式）迁移到 `astream_events`，利用事件流按 token 转发；处理了 planning 阶段 content 为空、推理模型 reasoning 字段不泄漏等边界
- **前后端流式协议配合**：理解前端 SSE 缓冲/合并机制，做到后端改造前端零改动

### 踩坑记录
- 重排序模型（2GB）同时被两个后端实例加载导致内存竞争、进程崩溃 → 验证时避免双实例并行
- pytest 在沙箱环境 tmp_path 权限受限 → 用独立脚本 + 内存 SQLite 复刻测试环境完成等价验证
- DeepSeek 服务端延迟波动大（同一请求 2.7~11.2s）→ 区分"本地可优化"与"上游不可控"，优化做到本地极限后如实标注剩余波动来源

### 量化成果速览（简历可用）
- 典型 AI 对话响应：24s → 8s（-67%）；最坏 49s → 9s（-82%）
- 单环节优化：HyDE 13.6s → 1.7s（-87%）
- 首字感知延迟：8.7s → 2.9s，且由"整段播放"变为"逐字流式"
- 全链路 3 处改动，无功能回退、无前端改动、无检索质量损失

## 6. 后续可优化方向（已记录在交接文档）
- 路由阈值与启发式：闲聊类短查询跳过 RAG 管线
- 合并路由打分与 Top-1 检索（省一次 embedding）
- 路由判断偶发 2~3.8s 波动定位（Chroma/Ollama 侧）
- 上游不可控的 Agent 首轮波动（DeepSeek 推理模型），可考虑换非推理模型或本地模型分流
